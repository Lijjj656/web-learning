2. 今天的硬规矩：WHERE 里必须两个条件

这是今天唯一必须刻进脑子的一条。

✗ 只写 id

UPDATE tasks
SET status = #{status}
WHERE id = #{id}

后果：编号通常连续自增，猜到别人的编号就能改别人的任务。等于把权限交给调用方。

✓ id + user_id

UPDATE tasks
SET status = #{status}
WHERE id = #{id}
  AND user_id = #{userId}

后果：编号决定"动哪条"，用户决定"能不能动"。不是自己的 → 影响 0 行 → 404。

AND 表示两个条件同时成立。删除是完全相同的写法：DELETE FROM tasks WHERE id = #{id} AND user_id = #{userId}。

为什么"不存在"和"是别人的"返回同一个 404

这是刻意设计，不是偷懒。如果分别返回"任务不存在"和"你没有权限"，别人就能靠状态码探测出某个编号的任务是否真实存在，属于信息泄露。统一 404 后，外界只能知道"这个编号对我不可用"。

情况SQL 影响行数接口返回页面表现
动的是自己的任务1200（PUT）/ 204（DELETE）绿色成功提示，列表或统计刷新
编号不存在0404红色错误提示
编号是别人的任务0404（同上，故意不区分）同样是错误提示
没 token / token 过期根本不执行401退回登录页
受影响行数是 MyBatis 返回的 int，表示这条 SQL 真正改动了几行。它是后端判断"到底有没有动到东西"的唯一依据——比任何前端判断都可靠，因为前端可以被绕过。

3.3 Service（TaskService.java 36–52）

public TaskResponse update(Long id, TaskRequest request, String authorization) {
    Long userId = currentUserId(authorization);      // 身份只认 token
    Task task = new Task();
    task.setId(id);                                  // 比 create 多的一步
    task.setUserId(userId);                          // 归属条件
    task.setTitle(request.title().trim());
    task.setCategory(request.category().trim());
    task.setPriority(request.priority().trim());
    task.setStatus(request.status().trim());
    if (mapper.update(task) == 0) throw notFound();  // 0 行 → 404
    return TaskResponse.from(requireOwned(id, userId));
}

public void delete(Long id, String authorization) {
    Long userId = currentUserId(authorization);
    if (mapper.delete(id, userId) == 0) throw notFound();
}

和昨天的 create 比只有两点不同：update 多了 setId（指定改哪条，而新增由数据库生成）；update/delete 多了"检查返回值"这一步。

3.4 SQL（TaskMapper.java 13–14、TaskMapper.xml 29–37）

<update id="update" parameterType="com.learning.jwtapi.Task">
  UPDATE tasks
  SET title = #{title}, category = #{category},
      priority = #{priority}, status = #{status}
  WHERE id = #{id} AND user_id = #{userId}
</update>

<delete id="delete">
  DELETE FROM tasks WHERE id = #{id} AND user_id = #{userId}
</delete>

SET 回答"改成什么"，WHERE 回答"允许改哪条"。少了 WHERE 会改掉整张表，少了 user_id 会改掉别人的。数据库列名 user_id 与 Java 属性 userId 只是命名风格不同，指向同一个字段。

6. 踩坑与定位

状态码定位表

看到含义该去哪查
401身份没通过token 还在不在、过没过期、请求头带没带
400请求内容不合格看「载荷」：多半是缺了某个必填字段（改状态时最容易踩）
404没动到任何行编号是否存在？是否属于当前用户？
500服务器内部出错看 Spring Boot 运行窗口的异常堆栈
这几个坑你已经踩过，或马上会踩：
  • MySQL 里直接 SELECT * FROM users; 报 1046 No database selected——先 USE learning_app;，或写全 learning_app.users。
  • 你的 user_id 不是 1（库里有 21 个用户）。查之前先 SELECT id,name FROM users; 确认自己的编号，否则会误以为"数据没入库"。
  • 改状态只发 status 一个字段 → 400。四个字段必须齐全。
  • 页面上看不到变化 ≠ 数据库没写进去。可能是列表没重载、统计没刷新，或归属不对被过滤。判断依据只有两个：Network 状态码 + 数据库查询结果。

7. 自测与收尾

合上讲义先自己答，再展开核对。答不上来的就是今天还没真正学会的部分。

① 为什么 update 比 create 多一行 task.setId(id)？

create 的编号由数据库自增生成，不需要指定；update 是改已有记录，必须先告诉 SQL 改哪一条。

② SQL 里去掉 AND user_id = #{userId} 会发生什么？

只要知道编号就能改/删任何人的任务。而编号通常连续自增，等于完全不设防。

③ 为什么删除返回 204 而创建返回 201？

201 表示"新建了资源，把内容回给你"，所以响应体是新任务对象；204 表示"成功了但没什么可回的"，所以响应体为空。

④ "不存在"和"属于别人"为什么返回同一个 404？

避免泄露"某个编号的任务是否真实存在"。统一 404 后外界只能知道"这个编号对我不可用"。

⑤ mapper.update() 返回的 int 有什么用？

是受影响行数。0 表示没匹配到任何行（不存在，或不属于你），Service 据此抛 404。它是后端判断成败的唯一可靠依据。
