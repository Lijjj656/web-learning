1. 先定位：今天补的是“结果怎样返回”

之前的主线是：网页 → Controller → Service → Mapper / MyBatis → MySQL。现在增加一条错误返回路径。统一异常处理器 ApiExceptionHandler 位于 Spring Boot 后端内部，负责把异常整理成 HTTP 响应。

图 1：错误处理是整条功能链的返回分支。发生异常后，正常路径中后续尚未执行的语句不会继续运行；Spring 寻找匹配的异常处理器。

为什么要单独写异常处理器？

新增、修改、删除都有可能失败。如果每个 Controller 都重复写相同错误响应，维护容易不一致。统一处理器让 Service 表达“发生了什么”，再由集中代码决定“怎么返回给网页”。

这不是新建一套业务，也不是把正常请求全部绕到异常处理器。只有匹配的异常发生时，它才负责生成错误响应。

本节的前后关系：前一节决定“允许改哪条任务”；本节决定“不允许或失败时怎样返回”；后续前端课程决定“接收响应后怎样恢复页面、提示用户”。

2. 状态码与消息：一份响应里的两部分

后端返回的 HTTP 响应包含状态码和响应体。状态码用于分类结果，响应体可以提供更具体的文字。例如删除不属于自己的任务：

HTTP 状态码：404
响应体（JSON）：
{"message":"任务不存在或不属于当前用户"}

这里不是“JSON 中有个 404 字段”。404 是 HTTP 响应状态，前端通过 response.status 读取；message 是 JSON 字段，前端解析后通过 data.message 读取。

状态本项目里的触发例子用户怎么处理
400请求标题空白、状态值非法、JSON 格式错误检查并修正输入
401密码错误；缺少、无效或过期 token检查账号密码或重新登录
404任务已被删除，或当前用户操作别人的任务刷新列表；不能操作他人任务
500后端出现未预料到的处理错误，例如数据库连接失败引发异常稍后重试；开发者查看日志排查

补充认识：200 常表示请求成功；201 表示创建成功；204 表示成功但没有响应体。项目注册重复邮箱会返回 409。今天先重点理解四类错误，不需要背所有状态码。

权限不足也可以采用 403；但本项目对“任务不存在”和“属于别人”统一返回 404，减少泄露任务是否存在。这个规则特指当前任务接口。

服务断开不等于一定收到 500。如果 Spring Boot 已关闭，浏览器可能根本收不到 HTTP 响应；经过 Vite 代理时也可能收到代理生成的错误。不要只凭一个数字就断定根因。

页面不一定多一个菜单。变化在于同一个按钮遇到失败时的反馈：不错误地显示成功，让用户知道接下来怎么办。

4. 从你写过的删除方法，追踪到网页提示

4.1 SQL：没有找到可删除记录

DELETE FROM tasks
WHERE id = #{id} AND user_id = #{userId};

假设任务 12 属于用户 3，而当前登录用户是 8。任务编号匹配，但用户编号不匹配，因此删除行数是 0。记录保持不变。

4.2 Service：停止正常流程并抛出异常

public void delete(Long id, String authorization) {
    Long userId = currentUserId(authorization);
    if (mapper.delete(id, userId) == 0) {
        throw notFound();
    }
}

你已经写过这段。现在展开 notFound()：

private ResponseStatusException notFound() {
    return new ResponseStatusException(
        HttpStatus.NOT_FOUND,
        "任务不存在或不属于当前用户"
    );
}

new ResponseStatusException(...) 创建异常对象，携带状态和原因；return 把这个异常对象交回调用处；前面的 throw 才真正抛出它并中断当前处理。只创建异常对象而不 throw，不会自动中断。

HttpStatus.NOT_FOUND 是 404 的 Java 名称。不要先背完整类名，先看出这是“状态 + 说明文字”的组合。

4.3 统一处理器：把异常变成响应

@ExceptionHandler(ResponseStatusException.class)
public ResponseEntity<Map<String, String>> responseStatus(
        ResponseStatusException error) {
    String message = error.getReason() == null
            ? "请求失败" : error.getReason();
    return ResponseEntity.status(error.getStatusCode())
            .body(Map.of("message", message));
}
写法在这次请求里的含义
@RestControllerAdvice标在处理器类上，让 Spring 使用它集中处理 Controller 请求中的异常
@ExceptionHandler(...)这个方法负责匹配指定类型的异常
error.getStatusCode()从异常取得 404
error.getReason()取得“任务不存在或不属于当前用户”
Map.of("message", message)准备 message 字段，Spring 将其转换成 JSON
ResponseEntity让我们指定 HTTP 响应的状态和响应体

这段代码可同时处理携带 401、404、409 等状态的 ResponseStatusException，不是每个状态都要写一个重复方法。校验异常和意外异常则由其他匹配的方法处理。

4.4 前端：响应失败时进入 catch

// App.vue：readJson 的处理摘录
if (!response.ok) {
    // 400、401、500 等有专门分支
    throw new Error(data?.message || "请求失败，请稍后再试");
}

// removeTask 的处理摘录
try {
    await apiRequest(`/api/tasks/${task.id}`, { method: "DELETE" });
    await loadTaskData();
    ElMessage.success("任务已删除");
} catch (error) {
    ElMessage.error(error.message);
}

这是分段摘录，不是完整函数。404 会使 apiRequest 内部的 readJson 抛出 Error，因此 await 后面的成功提示不会执行，转入 catch 显示错误。

原生 fetch 收到 404、500 时通常仍会得到一个 Response，不会仅因为状态是错误就自动进入 catch。项目的 readJson 主动检查 response.ok 并抛出错误，才把失败交给上层 catch。

5. 400、401、500 分别在哪一层产生？

400：请求内容没有通过规则

// TaskRequest.java
@NotBlank @Size(max = 200) String title

// Controller 方法参数
@Valid @RequestBody TaskRequest request

RequestBody 转换请求数据；Valid 检查规则。空白标题会触发校验异常，由处理器的 validation 方法返回 400 和消息。JSON 根本无法解析时，由 malformedInput 分支处理。

401：当前身份未通过验证

throw new ResponseStatusException(
    HttpStatus.UNAUTHORIZED,
    "Token 无效或已过期"
);

项目中 AuthService 负责验证凭证；任务 Service 通过它确认用户。无效凭证不能读写任务。多个条件同时不合法时，不要依赖它们固定的报错顺序；练习每次只制造一种错误。

500：未预料到的服务器错误

@ExceptionHandler(Exception.class)
public ResponseEntity<Map<String, String>> unexpected(
        Exception error) {
    log.error("API request failed", error);
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(Map.of("message", "服务暂时不可用，请稍后重试"));
}

这里保留详细日志，给页面通用提示；不是忽略异常，也不能把所有错误都当作 500。已有更具体的异常处理器优先匹配对应错误。

不要为练习 500 修改数据库密码、破坏表或在正式项目加一个故意崩溃的公开接口。今天通过代码与参考响应理解，隔离测试在后续测试课补充。

try {
